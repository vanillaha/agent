# 架构设计

## 1. 系统定位

本系统是课程课题 S01「科研文献搜集与证据问答 Agent」，它解决的问题是：

> 给定一个研究问题，在**本地文献库**和**联网文献源**之间自主选择检索路径，补充合法开放论文，
> 最终给出**每条事实都能追溯到原文位置**的回答；证据不足时明确拒答。

系统的核心产物不是"一段像样的回答"，而是**证据链**：任何一句结论都能反查到具体论文的具体页码或章节。

## 2. 形态与关键设计决策

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| Agent 还是固定工作流 | Agent（模型动态选择工具与步骤） | 课题名称后缀为 `Agent`，要求模型根据状态决定"继续检索 / 换路径 / 作答 / 拒答" |
| 模型与代码的分工 | 模型只负责理解、选择与生成；去重、合规检查、引用定位、覆盖率计算等由代码执行 | 课程硬性要求：确定性规则不得交给模型；LLM 输出必须过 schema |
| 两条检索路径 | 本地库检索与联网搜集相互独立，各自成链，由编排层选择 | 教师测试会分别"关闭联网"和"清空本地库"，两条链必须能独立工作 |
| 证据等级 | 全文证据、摘要信息、元数据、模型推断四档，必须显式标注 | 防止"本地证据与联网摘要混写"这一典型失分点 |
| 版本关系 | 预印本 / 会议版 / 期刊版归入同一个版本族 | 同一论文多版本入库会造成"多来源支持"的假象 |
| 知识库版本 | 检索与证据绑定 `kb_version` | 保证结果可复现，也便于评估时对比不同分块策略 |

## 3. 分层结构

```text
接入与契约层     M1 统一数据模型与接口契约 + M0 文档体系
        ↓
能力层           联网路径：M2 在线检索 → M3 合规下载 → M4 去重与版本
                 本地路径：M5 解析与索引 → M6 召回与重排
                              ↓
                 M7 证据充分性判断（决定是否继续检索）
        ↓
编排与产出层     M9 Agent 编排（LangGraph 图、停止条件、预算、人工确认）
                 M8 带引用的证据回答生成
        ↓
贯穿层           M10 检索记录与可追溯 · M11 测试与评估闭环
```

### 3.1 联网链路内部结构（M2）

```text
SearchService.search(request)                        ← 对外唯一入口，M7/M9 只调这里
      │
      ├─ QueryBuilder            PaperQARequest → 各源各自的 SourceQuery（纯规则，不含模型）
      │
      ├─ SourceRegistry          ONLINE_SOURCE_NAMES 固定顺序遍历，保证可复现
      │     ├─ OpenAlexAdapter          骨干：主检索 + OA 判定
      │     ├─ CrossrefAdapter          骨干：许可证来源（OA 恒为 unknown）
      │     ├─ ArxivAdapter             补充：全文 PDF 最好，恒为 preprint
      │     └─ SemanticScholarAdapter   补充：引用网络 + 跨源 ID 映射
      │
      └─ 共用基类 SourceAdapter（模板方法）
            ├─ 限流（RateLimiter，发请求之前）
            ├─ 失败封装（SourceError → error 字段，不抛穿）
            ├─ 字段长度处理（超长截断并记告警）
            └─ OA 筛选（服务端优先，否则本地筛并记告警）
                  │
                  └─ HttpClient（Protocol，可注入）
                        └─ CachingHttpClient → SQLite 响应缓存（TTL / replay_only）
```

设计要点：

- **适配器只实现两件事**：`build_request`（怎么拼请求）与 `parse_response`（怎么解析响应）。限流、失败封装、长度处理、OA 筛选全部由基类统一完成——否则四个源会长出四套毛病。
- **四个源各自翻译**：查询语法与筛选参数四家完全不同，共用同一份"检索意图"，而不是把同一个字符串硬塞给四家。
- **缓存与网络分离**：`replay_only=true` 时只读缓存、绝不联网，用于离线复现与测试。
- **失败域隔离**：某源挂掉只影响它自己的 `RetrievalRecord`，其余源照常返回。

## 4. 数据流：证据链

```text
PDF 文件
  └─ M5 解析 → Chunk（带 page_from/page_to/section_path、char 区间、来源文件摘要）
                    └─ M6 召回重排 → Evidence（quote 逐字引用 + Locator + 检索分数 + 轮次）
                                        └─ M8 生成 → Claim（断言 + evidence_ids 非空 + 支持等级）
                                                        └─ Answer（summary / conflicts / 拒答）
```

约束：

- `Chunk → Evidence → Claim → Answer` 每一环都必须能向上游回溯。
- `Evidence.source_type = fulltext` 时必须有 `chunk_id` 且 `is_local = true`：**联网搜到的摘要不能当作全文证据**。
- `Claim.evidence_ids` 不允许为空：**无证据的断言不允许存在**。
- 拒答时不得输出任何 `Claim`。

### 4.1 联网链路的中间数据流（M2 已实现部分）

本地库链路要求"先有 PDF 才能有证据"，联网链路则要先解决"哪些论文值得下载"：

```text
PaperQARequest（研究问题 / 关键词 / 年份与类型筛选 / allow_online）
  └─ M2 QueryBuilder → 每个源一份 SourceQuery
       └─ 四个适配器并发域内串行检索 → SourceCandidate（PaperRecord + 许可证 + OA 依据）
            ├─ 归一化：DOI/arXiv ID 清洗、年份解析、作者去重、标题压平、类型分类
            ├─ 开放获取判定：保守规则，见 doc/接口与字段.md「开放获取判定规则」
            ├─ 每源一条 RetrievalRecord（query / result_count / kept_count / error）
            └─ SearchOutcome（跨源候选，未去重）
                 └─ M4 去重与版本归并 → 合并后的 PaperRecord
                      └─ M3 合规下载 → 本地 PDF → 汇入上面那条本地链路
```

关键约束：

- **`result_count` 与 `kept_count` 必须都记录**：前者是上游给了多少，后者是我们敢用多少，差值就是解析质量问题，是 M11 评估的关键指标。
- **搜索 ≠ 下载**：M2 只产出候选与"能不能下载"的判断依据，实际下载合不合规由 M3 决定。
- **每个来源独立留痕**：即使整轮检索成功，也要能看到哪个源挂了、哪个源被禁用。

## 5. 技术栈与依赖

| 层次 | 选择 | 备注 |
| --- | --- | --- |
| 语言 | Python 3.11（规范要求） | 实际验证环境为 3.13.16，见 `pyproject.toml` 的 `requires-python = ">=3.11,<3.14"`；Docling、LangGraph 对版本敏感，若 M5 不兼容需回落 3.11 |
| 数据校验 | Pydantic 2.x | 所有输入、输出、错误、证据必须过校验 |
| 服务 | FastAPI + HTTPX | 任务式 REST 接口 |
| 工作流 | LangGraph | 编排层（M9） |
| 文档解析 | Docling | 必须保留页码、章节、表格位置 |
| 在线数据源 | OpenAlex / Semantic Scholar / arXiv / Crossref | 每个数据源一个独立 adapter |
| 生成模型 | OpenAI-compatible 服务（本项目使用 DeepSeek） | 只负责选择与生成 |
| 向量模型 | BGE-M3 | M5/M6 的 embedding，可替换 |
| 存储 | SQLite | 元数据、分块、检索记录、任务状态 |
| 测试 | pytest | 契约测试 + 行为测试 |

依赖记录：

| 依赖 | 用途 | 影响 | 版本约束 |
| --- | --- | --- | --- |
| pydantic | 全部 schema 校验 | 核心依赖，升级需重跑契约测试 | `>=2.10.6,<3.0.0` |
| httpx | M2 在线检索的 HTTP 客户端（超时、重试、同步请求） | 仅联网链路（M2、M3）使用；本地链路与测试不依赖它。测试通过注入假客户端完全绕开网络 | `>=0.27,<0.29` |
| pytest | 测试框架 | 仅开发期 | `>=8.3,<9.0` |

M2 未引入除 `httpx` 之外的新依赖：SQLite 用标准库 `sqlite3`，XML 解析用标准库 `xml.etree.ElementTree`，哈希用标准库 `hashlib`。M3、M5 及之后引入 `docling`、`langgraph` 等依赖时，在对应任务中新增记录。

## 7. 已知限制

- M1 只做字段级与单对象级校验。跨对象约束（如"一个版本族至多一个权威版本"、"`Claim` 引用的 `evidence_id` 必须真实存在"）属于服务层职责，在后续模块任务中实现。
- REST 契约已冻结但未实现，接口文档与实际路由的一致性需在实现后复核。
- **M2 的去重与后处理未做**：`SearchOutcome.candidates` 是**未去重**的跨源汇总，同一论文会在多个源各出现一次。合并、字段择优与版本族归并属 M4，调用方不得直接把它当最终文献清单。
- **M2 不做合规判断**：适配器只如实上报 `oa_status`、`oa_url`、`license`，是否允许下载由 M3 依据 M3 的合规规则决定。Crossref 的 `oa_status` 恒为 `unknown`（Crossref 不做 OA 判定），这是有意的——许可证信息才是它的价值。
- **M2 的 `paper_id` 依赖上游元数据质量**：标题+年份是弱键，同名综述可能被误合；这是"无 DOI 时的最优选择"，不是缺陷但需在 M4 复核。
- **缓存无并发控制**：SQLite 响应缓存面向单进程使用；若后续多进程并发检索，需重新评估。
- **限流按源而非按进程**：多个进程各自限流会叠加成高于礼仪的请求频率；生产化时需外部化限流。
